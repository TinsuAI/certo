## [2026-07-08] BOM version precedence: honour the pin, not the newest
**Context:** A sheet auto-calculates against a product BOM version chosen by a precedence chain. The chain was duplicated in two functions that had drifted: `attach_case_bom_snapshot` (`bom_store.py`) ran first with a 3-step chain (no client-default step) and *wrote* `product.bom_product_artifact_id`; `selected_bom_rows_by_product` (`co_case_context.py`) then read that already-written field as its step 1, so its own client-default step never fired. Effect: staff pin v1 as the client default, DH publishes v2 → the sheet silently calculates v2, the ★ sits on the unselected v1. The written field is load-bearing (the version dropdown's `selected` value and the "có BOM" badges read it), so "just stop pre-pinning" is not viable.
**Decision:** Precedence is **explicit pin (case override) > client default > DH aggregate composition > DH latest usable**. A pinned/client-default version is honoured even after DH publishes a newer one — newest does NOT auto-win. Enforce it through **one** resolver `resolve_selected_product_version(product, …) -> (version, source)` called by both the snapshot writer and the per-sheet selector; it also returns `source` (which step won) to drive the picker's "why" label.
**Alternatives:** (a) Latest-wins — auto-adopt DH's newest published version; rejected because it makes an explicit pin meaningless and breaks trừ-lùi determinism. (b) Narrow patch — add the missing client-default step to `attach_case_bom_snapshot` only; rejected because two copies of an 8-step chain will drift again.
**Consequences:** Existing live cases whose client-default differs from DH-latest will start calculating the *pinned* version (the intended correction; locked/snapshotted cases are frozen, unaffected). The unified resolver is the seam the #1b batch BOM-selection picker builds on (provenance label comes free).

## [2026-07-08] Substitute discovery is stock-first; stock-sourced substitutes are declarable
**Context:** The substitute picker discovers candidates from DH substitutes + DH catalog + CO history, then annotates them with stock; it never builds candidates FROM stock. So an NVL in stock but absent from the DH catalog is invisible and cannot be substituted. A prior handoff (#3) claimed such stock-only codes would be `declarable_unmatched` and blocked by the DC3c lock/export guard, and proposed flagging them + a reverse "register in Data Hub" flow as a precondition. Re-checking the code: `declarable_unmatched` is a **Data-Hub catalog classification** (`customs_relevance == "declarable_unmatched"` = "real, declarable, but no BCCT import match"); CO only echoes it, never manufactures it, and an unclassified material is KEPT not dropped (`origin_material_filters.py`). A substitute sourced from `co_stock_rows` has a BCCT import match by construction (stock IS materialised import lots carrying hs/CIF/customs_item_code), so it is the opposite of unmatched.
**Decision:** Flip discovery to **stock-first ⟕ catalog**: build candidates from the CO-stock snapshot grouped at the logical-material grain (`allocation_code` when resolved, else `customs_item_code`), LEFT-JOIN the catalog for name/HS/origin enrichment, dedup against the DH "Khuyến nghị" list, order stock-first (not a hard filter — catalog-no-stock stays visible, dimmed). A stock-sourced substitute is **fully declarable with NO blocker flag**: build its material row from the stock lot's own name/HS/unit_value; the catalog join only enriches. Missing origin_status defaults conservative (non_origin), safe for LVC.
**Alternatives:** (a) Handoff #3's flag-and-block + reverse-DH-registration-as-precondition — rejected: mis-scoped `declarable_unmatched` (wrong polarity); imported/warehoused goods are declarable by construction. (b) Hard filter to only-in-stock in search — rejected: loses the ability to see catalog-only materials. (c) Special-case the rare DH-vs-stock contradiction (a stocked code DH classifies as unmatched/rác) — deferred: flipping "stock evidence beats DH classification" is a trust-model change, out of scope; keep trusting DH, surface via the existing review row (→ BACKLOG).
**Consequences:** stock-only NVL become findable and substitutable; #3 (the deferred compliance nuance) largely dissolves; the reverse "missing-material → Data Hub" flow, if built later, is a name-normalisation convenience, not a C/O-issuance precondition.

## [2026-07-10] Bảng kê row grain: CO already matches agency practice (one row per BOM line)
**Status:** Supersedes an earlier draft of this entry that decided "one row per lot". That draft rested on a misreading of the agency's workbook and was withdrawn before any code was written. The misreading is recorded because it is easy to repeat.
**The misreading:** grouping the agency's rows by the material-code prefix before `#&` shows 39 codes on more than one row, 31 of them with differing unit prices, which looks like per-lot splitting. It is not. The 13 `TEM` rows are **six different materials** (tem 60×25mm, tem 60×16mm, tem chịu nhiệt 10×12mm, …) sharing a code prefix, and one of those names occupies 5 rows with identical định mức, đơn giá and tờ khai — five occurrences of one component in the BOM, not five lots.
**What the agency actually does** (`barry-CO-data/.../Bang RVC GIN01426B283 (đã chỉnh).xlsx`, sheet `PV00.0048400`): **361 rows for 281 distinct material names** — one row per BOM line. When a BOM line draws on several lots, **86 of the 361 rows merge two or more declaration numbers into a single cell (10)** and print **one** đơn giá. That is CO's own grain and CO's own `", ".join(allocation_import_declarations)`.
Research (`.ai/knowledge/2026-07-10-co-origin-cumulation-and-vn-origin-rules.md`, Addendum (b)): **no binding text prescribes the row grain.** TT 05/2018 Điều 7 only names the form; NĐ 31/2018 Điều 15.1.e says "bảng kê chi tiết" and delegates the mẫu; eCOSys accepts the bảng kê as a signed attachment, not a row-validated record. The Phụ lục VIII *Ghi chú* requires the trader to submit the import declarations and document copies *"để đối chiếu với thông tin kê khai từ cột (9) đến cột (13)"*. The agency satisfies that duty with merged cells, so per-cell single-valuedness is not in fact demanded.
**Decision:** Keep one bảng kê row per **BOM line**. CO does not diverge from the submitted document; no grain migration, no override re-keying, no web-grid rework. Whether a row ever splits is decided solely by whether its lots resolve to different origins — a separate, still-open question.
**Consequences:** Two defects surface that are independent of grain and of origin, and both must be settled before origin work, because apportioning origin inside a row requires the per-lot values to be right. (i) Column (6) can contain **text**: `allocation_unit_value_summary` (`co_case_context.py:2638-2644`) writes the literal `"Nhiều đơn giá"` when a BOM line's lots disagree on price, and `allocation_currency_summary` writes `"Nhiều tiền tệ"`; the agency prints a single number there. (ii) `stock_allocation_line` prices a lot **BOM-first** (`:2507-2513`: `bom.unit_value → bom.unit_price → co_stock.unit_value → …`), so a BOM planning price outranks the lot's import CIF, which is what column (6) is defined to carry.
`allocation_lines` already reach the renderer (`:2450`) carrying declaration no/date/line, customs code, allocated qty, unit and material value, currency and FX. Two fields are missing from them: `origin_country` (present on the stock row, `co_stock_derivation.py:65`, not copied by `stock_allocation_line`) and `consignee_name` (present on the BCCT row, dropped by `co_stock_derivation`).
## [2026-07-10] VN origin is decided per row: BCCT origin AND a supplier flagged as supplying Phụ lục X
**Context:** Domestic materials bought from Vietnamese suppliers are already in `hub.bcct_rows` as on-spot imports (`direction='import'`, `declaration_type` E15/E13, `origin='VIETNAM'`, supplier in `consignee_name`) — 6,272 rows / 1,252 materials / 64 suppliers for Johnson. CO reads `origin` (→ `origin_country`) but never lets it touch `origin_status`, so all of it is summed into VNM and RVC is understated. Both inputs the fix needs already reach CO; no Data Hub change is required (see `.ai/knowledge/2026-07-10-vn-origin-supplier-data-facts.md`).
The bảng kê (Phụ lục VIII, TT 05/2018 — verified against the promulgating `rev5` .docx) carries **three separate columns**: (7)/(8) the money split *có / không có xuất xứ FTA*, (9) *nước xuất xứ*, and (12)/(13) the **Số/Ngày of the C/O ưu đãi nhập khẩu or the Bản khai báo (Phụ lục X)**. Phụ lục X carries a *ngày* but **no số**, and certifies the goods were produced at the signer's own factory. Its Ghi chú excludes **Form D**.
**Agency practice (from a real submitted dossier, `barry-CO-data/.../Bang RVC GIN01426B283 (đã chỉnh).xlsx`)** settles two things the forms leave open. Column (9) is **not** filled with the country: the macro emits the raw BCCT country string, then a human rewrites every non-qualifying row to the literal phrase **`Không xuất xứ`** (6 of 7 sheets converted; one left un-corrected, which is how the two conventions are visible side by side). A qualifying row reads (9) `Việt Nam`, (7) the value, (12) **`Phụ lục X/Công ty TNHH Minghui Việt Nam`**, (13) `18/07/2025` — i.e. the evidence reference is composed at **supplier grain**, precisely because Phụ lục X has no số. The same dossier shows the AND rule already being applied by hand: the un-corrected sheet has 17 `VIETNAM` rows, the corrected sheets keep exactly **one** `Việt Nam` row — the one supplier with a Phụ lục X.
**Decision:** Phase 1 marks **suppliers**, not lots. A supplier carries one flag — *"has supplied C/O or Phụ lục X for VN origin"* — asserting **evidence availability**, not the supplier's nationality — plus the Phụ lục X date. A material row is originating iff **`origin_country` normalizes to VN AND its supplier is flagged**; everything else keeps the conservative `non_origin` default. The flag lives in **CO**, keyed on the normalized `consignee_name` (no counterparty tax code exists anywhere in the data). Column (9) emits `Không xuất xứ` for non-qualifying rows and the country for qualifying ones; (12)/(13) emit `Phụ lục X/<tên NCC>` and the flag's date, replacing today's blanks (`bang_ke_renderer.py:299-300`).
**Alternatives:** (a) Per-lot evidence references now (`{số hóa đơn GTGT, ngày PL X}` per lot) — legally complete, rejected for phase 1: it requires backfilling 6,272 historical rows for Johnson alone. (b) Supplier flag alone, without the `origin_country` AND — rejected on evidence: **24 of the 64** VN-capable suppliers sell mixed-origin goods (Johnson's own affiliate: 1,399 VN rows and 1,611 CHINA/GERMANY/TAIWAN rows), so flipping a whole supplier would promote thousands of Chinese-origin rows. It also contradicts NĐ 31/2018 Điều 15.1.g — a Vietnamese seller's nationality confers nothing. (c) Store the flag in Data Hub — rejected: DH models no supplier entity, only a text column; the `client_material_group_map` precedent classifies *materials*, which DH does model. DH becomes the right home once evidence documents, retention, lot-level overrides, or a second consumer arrive.
**Row splitting when a BOM line's lots disagree on origin:** grain is the BOM line (see the row-grain ADR above). A BOM line can draw on several lots; when those lots resolve to **different** origins (e.g. one VN lot from a flagged supplier, one CHINA lot), the line is **split into one row per resolved origin**, each row keeping the merged-tờ-khai behaviour within its part. Rejected alternatives: (a) apportion inside one row — column (9) then has no correct single value, since the agency writes `Việt Nam` or `Không xuất xứ` there, not both; (b) whole line takes the worst-origin lot — conservative and cheap but discards the VN portion of a mixed line. Row identity for a split row is `(material_sequence, origin_status)`, not the positional index; `material_sequence` already exists (`co_case_context.py:1069`) and overrides are all material-scoped, so this is the only place a non-index key is needed.
**Consequences:** This is the **first** CO change that moves value *out of* VNM and pushes RVC *up* — the direction an ex-post customs verification exists to challenge. Because the agency composes the evidence reference at supplier grain, the claim and its proof ship together: no row lands in column (7) without `Phụ lục X/<NCC>` + ngày in (12)/(13). Resolution is evaluated **per row** and never written onto the material, so moving the flag to DH later only changes where it is read from. The resolver returns an originating **amount**, not a boolean — needed for the split rows and reused unchanged by ATIGA partial cumulation (Form D) later. Column (9)'s real content is a **qualification label** (`Không xuất xứ` / `Việt Nam`), not the country the header names — CO's `origin_default` catalog strings already speak this vocabulary. Phase 2 caveat: Phụ lục X is **not** the instrument for Form D, and CO models no Form D or AK yet (`co_forms.py:9-40`).
**Still open:** a BOM line's consumed quantity that no lot covers (shortage, or no matching lot at all). It has no declaration, so columns (10)–(13) are empty and it cannot be originating — it must land in column (8), never (7). Whether it renders as its own `__unmatched__` row or blocks lock/export is undecided (Câu 2, not yet answered).

## [2026-07-11] Shortage (consumption exceeding import lots) blocks issuance; fix decoupled from any status refactor
**Context:** A BOM line whose consumed quantity exceeds the matched import lots leaves a shortfall with no import declaration and no supplier/VAT-invoice backing. Research (`.ai/knowledge/2026-07-10-co-origin-cumulation-and-vn-origin-rules.md`, Addendum 2026-07-11) verified against promulgating texts: such a quantity has **no lawful value** on the bảng kê (TT 05/2018 Điều 6.4.b recognizes only import-CIF-tied or VAT-invoice-tied values; "giá mua đầu tiên" is origin-unknown, not document-unknown), and it is the signature of an unbalanced quyết toán (TT 38/2015 Điều 55/59/60). Today `calculated_sheet_status` (`co_case.py:2038-2059`) does NOT count shortage, so a shortage sheet reaches `calculated` and is lockable/exportable — shipping an unlawful bảng kê. Two pricing paths currently misvalue it: a partial shortage sums only matched lots (shortfall valued at zero → inflates RVC); a no-lot material gets `consumed_qty × fallback_unit_value` from BOM/catalog (a price that cites no declaration).
**Decision:** Shortage blocks issuance, using the established **three-belt** guard that `declarable_unmatched` already uses (the one-belt status downgrade is bypassable — save/bulk-substitute routes hardcode `status="calculated"` at `co_case.py:3104,3119`): (1) flag in `calculated_sheet_status`, (2) re-check in the lock gate `origin_sheet_action_error` (`co_case_context.py:1430-1444`), (3) add to `origin_sheet_export_blockers`, (4) tests mirroring `test_declarable_unmatched_guard.py`. Add a shortage-specific lock-block reason so the user is not looped through "press Tính → re-block". Remove the fallback-price path for no-lot materials (they are 100% shortage → blocked anyway). The remedy surfaced to the user is to supply the missing document (match the import declaration / enter the VAT invoice), never to estimate a price.
**Hard constraint (from adversarial review, Fable-5 critic):** this fix must NOT ride behind, or land in the same change as, removing the status-downgrade branches from `calculated_sheet_status`. Reason: `missing_price` is enforced ONLY by that downgrade (the lock gate does not re-check `lvc_missing_price`), so deleting it without adding a re-check makes missing-price lockable via the save-route bypass.
**Alternatives:** (a) One-line shortage check in `calculated_sheet_status` — rejected: bypassable via the save/substitute hardcode, same hole DC3c already had. (b) Value the shortfall at a fallback/estimated price into column (8) — rejected: unlawful, no document to cite (this was an earlier proposal, withdrawn on the user's objection and confirmed by research). (c) Couple the fix to the status-model refactor — rejected on sequencing: an urgent legal defect must not wait on a risky gating rework.
**Consequences:** Shortage sheets stop being issuable; `calculated_sheet_status` returns `bom_loaded` for them, so the badge reads "Đã nạp BOM" after calculate — a known imperfection shared with the other three block conditions, addressed separately by the readiness chip below, not by this ticket. Two follow-ups this surfaces, neither in scope of the guard but neither droppable: (i) an **audit of already-locked shortage sheets in prod** (claims already written to `co_stock_claims`) — the largest standing legal exposure; (ii) **deliberate resolution of the missing-price one-belt hole** (currently blocked on `/calculate`, leaks via save-route) — resolve as a decision, not a refactor side effect.

## [2026-07-11] Status model: badge honesty via a readiness chip, NOT by re-keying the status enum (deferred)
**Context:** `bom_loaded` is overloaded — it means both "BOM loaded, not yet calculated" and "calculated but not issuable" (the block conditions downgrade to it), so a sheet the user just calculated can show "Đã nạp BOM". A two-dimension split (calculation lifecycle vs issuance readiness) was proposed to make the badge truthful.
**Decision:** Do the cheap, safe half now if desired — a **persistent blocker chip** rendered from `origin_readiness_status` (which already classifies shortage/missing-price/etc. as `blocked`) plus a specific reason, WITHOUT changing what `calculated_sheet_status` returns. Defer the full status-enum refactor to after the VN-origin feature. If ever done, it must: consolidate onto the existing `origin_readiness_status` (not add a third representation), keep gates deriving flags at action time (never trust persisted status — the save-route bypass is the lesson), treat `missing_bom` as a **failed calc** not "calculated + blocked" (labeling an empty-BOM sheet "Đã tính" is a new lie), and fix the calculability regression (`co_case_context.py:1327`: a `calculated` shortage sheet would disable the Tính button that the shortage remedy needs).
**Alternatives:** (a) Refactor as a prerequisite to the shortage fix — rejected (see the hard constraint above). (b) Leave the badge as-is — acceptable; the chip is a UX improvement, not a correctness fix.
**Consequences:** Badge honesty is decoupled from gating correctness. The refactor, if it happens, is its own well-scoped ticket with the four conditions above, sequenced after VN-origin.

## [2026-07-11] Column (9) content is a client-default + per-case mode, materialized at Tính
**Context:** Column (9) "Nước xuất xứ" is blank in production — all three renderers read `origin_country` (`bang_ke_renderer.py:287`, `workbook_io.py:649`, `bang_ke_xml_generator.py:511`) but neither `origin_material_from_bom_row` nor `stock_allocation_line` copies it from the lot (`co_stock_derivation.py:65`). Research says (9) should hold the country of origin (qualification lives in the (7)/(8) money split); some agencies instead hand-write the literal "Không xuất xứ" for non-preferential / no-originating-material cases. The user wants both as a UI choice. Design produced by a fable design agent, grounded in the code.
**Decision:** Two modes — `country` (Vietnamese country name; default) and `qualification_label` ("Không xuất xứ" / "Việt Nam"). Scope = **client-config default + per-case override, no per-sheet knob** (precedent: the per-sheet `currency_mode` override at `co_case.py:882,3236`). Resolver `resolve_origin_column_mode(client_config, case)` is the only place precedence lives. The mode is read **once per Tính** in `_recompute_origin_sheet_context` (`co_case.py:2060`), threaded down the existing funnel (`origin_product_from_invoice_match` → `origin_material_from_bom_row`) as a kwarg, and the resulting string is **materialized** onto each row as `bang_ke_origin_text` and stamped as `product["origin_column_mode"]`. All three export renderers and the web-grid cell become pure readers of `bang_ke_origin_text` — no renderer reads config, so export == web grid holds by construction. `column9_text(mode, origin_status, country_label_vi)` is one function; it must NOT touch `origin_status`, so money columns (7)/(8) and LVC are identical across modes (regression test: same case both modes → identical (7)/(8) footer totals).
**This resolves the split-key inconsistency in the row-splitting ADR above.** Row identity becomes `(material_sequence, origin_status, column9_text)` — ONE rule, no mode conditional. In `qualification_label` mode `column9_text` is a function of `origin_status` alone, so the key degenerates to the recorded `(material_sequence, origin_status)`; in `country` mode CHINA vs TAIWAN lots (same origin_status, different country) split correctly.
**Normalization** (country mode only): code-owned `app/origin_country.py` with `RAW_TO_ISO` (seeded from the observed BCCT vocabulary) + `ISO_TO_VI`, applied at Tính. Unmapped string → print the **raw BCCT string** + a non-blocking `material_warnings` entry. **Never** a lock/export block — a display-name gap changes no number (this was the fable-critic's refused item). Not in client_config, not admin-editable: it is shared legal/geographic vocabulary, git-versioned and tested.
**Mixed-mode dossier:** snapshot-at-Tính records the mode per sheet. Flipping the mode marks mismatched `calculated` sheets `stale` (already disables lock and blocks export); `draft`/`bom_loaded` untouched; **locked sheets untouched** (their snapshot is what was filed) + a visible mismatch chip and a warning listing them. A three-belt re-check (mirroring the shortage/`declarable_unmatched` guards) covers the save-route status hardcode bypass — but never blocker-izes locked sheets.
**Alternatives:** (a) Always `country`, no toggle — rejected: agencies legitimately file non-preferential dossiers with the "Không xuất xứ" convention that customs accepts. (b) Per-sheet mode — rejected: a dossier is one C/O; mixing conventions across its sheets is only a hazard, never wanted; the variation is per-case (form/market), not per-sheet. (c) UI-editable normalization table — rejected: the BCCT origin vocabulary is a finite historical corpus (~30 entries), a code dict with tests covers it; storage+admin UI+audit is over-engineering.
**Consequences:** Prerequisite ordering — the mode rides on the `origin_country` plumbing and the override re-key from positional index to `material_sequence` (both already required by the row-grain/split ADRs); it can ship before the per-row VN-origin resolver (it works against today's catalog `origin_status`). Migration: no backfill — old persisted sheets keep rendering blank (`bang_ke_origin_text` → legacy `origin_country` → "" fallback), first Tính after deploy materializes them; `migrate_config` auto-adds the default. Open sub-decisions recorded for the human: qualification-mode originating label hardcoded "Việt Nam" (fine while qualification mode is scoped to non-preferential); UNKNOWN/KHONG XAC DINH → "Không xác định" + warning; flip-while-locked = allow-with-warning.

## [2026-07-11] Override identity = material_sequence, made BOM-version-aware; no new persisted id
**Context:** The row-split and column-9 work re-key per-material overrides (rename/norm/code/delete/substitute) off the positional render index. Question raised: is `material_sequence` a good enough identity, or is something better needed? Traced (agent + direct read): `material_sequence` is a per-product positional enumeration of BOM rows (`co_case_context.py:2080`, `enumerate(bom_rows, start=1)`), re-derived each recalc, string, unique per sheet. It equals today's override index+1. The source BOM carries a stable **version** id (`product_artifact_id`) but **no per-line id** — a component line is identified only by `material_code` (deliberately non-unique) + position.
**Decision:** Use `material_sequence` for BOM-derived materials; keep `added_<n>` for manually added rows (their sequence is unstable — deleting an earlier added row renumbers later ones). Do NOT introduce a new persisted per-material UUID. Rationale: a BOM version is an **immutable artifact** (any composition change mints a new `artifact_id`; lines within one version never reorder), so position-within-version is stable by construction while the version is fixed — the robustness ceiling the source data allows. A UUID buys nothing beyond `(version, position)` and adds a migration + first-assignment problem. **The one upgrade worth taking:** make the override binding version-aware — key by `(bom_product_artifact_id, material_sequence)` or drop overrides on a version switch. `material_overrides` today key on position only and are not obviously version-scoped (`co_case.py` bulk-substitute + `material_row_index`), so "line 3 of v1" can misapply to "line 3 of v2" after a version change — a latent bug independent of the split; close it here.
**The split does NOT destabilize this.** Row-splitting by origin is a **render-time fan-out**: one source material emits N display rows, `product["materials"]` is unchanged, so the source material's identity is as stable as today. (Earlier framing calling the override re-key "the riskiest task" was overstated — corrected: it is mechanical, not a source-list mutation.)
**Alternatives:** (a) New persisted UUID — rejected: no more robust than `(version, sequence)` given no source line id, plus cost. (b) `material_code` as key — rejected: non-unique by design (`co_stock_ledger.py:84`). (c) Bare `material_sequence` without version-awareness — rejected: the version-switch misapply gap.
**Consequences:** Cheap, no new schema; the version-aware binding also fixes a pre-existing override-vs-version-switch bug. Migration of legacy positional override keys is deterministic (`str(int(key)+1)`).
